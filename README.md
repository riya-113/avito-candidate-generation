# Кандидатогенерация для категории «Услуги» (Авито, Recall@50)

Задача: для каждого поискового запроса выбрать из корпуса 189 212 объявлений до 50 кандидатов так, чтобы в них попали объявления, которые пользователь в итоге выбрал. Метрика — Recall@50.

**Итоговый результат на платформе: Recall@50 = 0.8810** (бейзлайн TF-IDF — 0.3807).

Решение — гибридный поиск: дообученный на парах из train эмбеддер `multilingual-e5-base` + лексический TF-IDF + географический бонус (расстояние до центра локации запроса) + популярность объявления.

## Быстрый запуск (воспроизведение answer.csv)

Требования: Windows/Linux, Python 3.12, видеокарта NVIDIA с CUDA (решение проверялось на RTX 5080, 16 ГБ).

```bash
python -m venv .venv
.venv\Scripts\activate            # Linux: source .venv/bin/activate
pip install torch==2.11.0 --index-url https://download.pytorch.org/whl/cu128
pip install -r requirements.txt
```

**Данные.** Положите три файла в папку `data/`: `train.parquet`, `benchmark_queries.parquet`, `benchmark_items.parquet`.

**Модель.** Дообученная модель (~1 ГБ) не помещается в GitHub. Есть два варианта:

1. *Скачать готовую (точное воспроизведение):* архив `e5-avito.zip` по ссылке https://disk.yandex.ru/d/2uQTXr-jab4YpA. Распакуйте его в папку `models/`, чтобы получился путь `models/e5-avito/model.safetensors`:
   ```bash
   # PowerShell
   Expand-Archive e5-avito.zip -DestinationPath models
   ```
2. *Обучить заново:* `python step4_finetune.py` (около 2 часов на RTX 5080). Из-за недетерминизма обучения на GPU веса получатся чуть другими, поэтому ответ может немного отличаться от отправленного. Для точного воспроизведения используйте вариант 1.

**Запуск:**

```bash
python step3_hybrid.py submit 0.95 2.0 4.0   # создаёт answer.csv
python check_answer.py                       # проверка формата
```

Все параметры итогового решения стоят в коде по умолчанию, переменные окружения задавать не нужно. Эмбеддинги кэшируются в `cache/`, кодирование корпуса занимает около 2 минут.

**Проверка воспроизводимости.** Модель была распакована из архива, кэш эмбеддингов удалён, после чего команда выше дала `answer.csv`, совпадающий с отправленным на платформу на 100% (скрипт `compare.py`). Эмбеддинги считаются в fp16 на GPU, поэтому на видеокарте другой архитектуры последние знаки могут немного отличаться, что способно поменять единичные объявления в топ-50.

**Без интернета.** Для `submit` с локальной моделью доступ в интернет не нужен, внешние API не вызываются. Интернет нужен только `step4_finetune.py`: он один раз скачивает открытые веса базовой модели `intfloat/multilingual-e5-base` с Hugging Face.

## Структура

| Файл | Что делает |
|---|---|
| `check_env.py` | проверка окружения, GPU и данных |
| `step1_eda.py`, `step1b_checks.py` | разведочный анализ данных |
| `step2_baseline.py` | лексический бейзлайн TF-IDF и общие функции |
| `step3_hybrid.py` | итоговое решение: гибридный поиск, валидация, анализ ошибок, `submit` |
| `step4_finetune.py` | дообучение эмбеддера на парах «запрос → выбранное объявление» |
| `diag_loc.py`, `diag_geo.py` | диагностика географических признаков |
| `check_answer.py`, `compare.py` | проверка формата и сравнение двух ответов |

Режимы `step3_hybrid.py`: `val2` — валидация, `err` — анализ ошибок, `submit w loc dist` — ответ для бенчмарка. Модель выбирается переменной окружения `MODEL` (по умолчанию `models/e5-avito`; для базовой модели `MODEL=intfloat/multilingual-e5-base`).

## 1. Данные и признаки

Сначала проведён разведочный анализ (EDA), от его результатов зависел выбор признаков.

- **Категория выброшена.** 99% корпуса лежит в категории 114, и в 497 620 из 497 673 пар train категория запроса и объявления одинакова. У 9% запросов бенчмарка категория пустая (0), так что жёсткий фильтр по ней не отсекает ничего полезного и способен только навредить.
- **Текст объявления:** заголовок, параметры (`item_infm_params_text`) и начало описания. Медианная длина заголовка 4 слова, этого мало. Конкретика («Вид услуги», «Тип услуги», названия услуг из прайса) лежит в параметрах. Описание длинное и шумное, но добавляет слова, которых нет в других полях.
- **Текст запроса:** `search_query` плюс фильтры `search_infm_params_text`. Фильтр «Вид услуги …» дословно совпадает с параметрами выбранного объявления в 98.4% случаев.
- **География:** город запроса совпадает с городом выбранного объявления в 83% пар train. У запроса есть только `search_location_id`, поэтому координаты «центра» каждой локации восстановлены по train как медиана координат объявлений, выбранных в этой локации.
- **Популярность:** число отзывов `item_rating_reviews_count`.
- **Пары из train используются как обучающие данные для эмбеддера**, а не как справочник ответов: по `item_id` в корпусе есть только 6.6% объявлений из train, а тексты 63% запросов бенчмарка в train не встречаются.

## 2. Модели и алгоритм

Для каждой пары запрос–объявление считается итоговая оценка, и берутся 50 объявлений с максимальной оценкой. Поиск точный (перебор всего корпуса на GPU через матричное умножение), без приближённых индексов, чтобы не терять полноту.

```
score = 0.95 · z(семантика) + 0.05 · z(TF-IDF)
      + 2.0 · [город объявления == город запроса]
      + 4.0 · exp(−расстояние_км / 200)
      + 1.0 · log(1 + отзывы) / log(1 + max_отзывы)
```

- **Семантика:** `intfloat/multilingual-e5-base` (open-source), дообученная на train (см. ниже), fp16 на GPU. Текст объявления: `passage: заголовок. Вид услуги. Тип услуги. описание[:500]`, запрос: `query: текст + фильтры`. Полные параметры в эмбеддер не подаются: они длинные и заполняют лимит токенов адресами и списками марок авто.
- **TF-IDF:** слова обрезаются до 5 символов (грубая замена лемматизации, «наращивание» ≈ «наращивании»), `sublinear_tf`, `min_df=2`. Заголовок повторён трижды для большего веса.
- **z(·)** — нормировка оценок внутри запроса (среднее 0, разброс 1), чтобы складывать сигналы разной природы.
- **Расстояние** — от центра локации запроса до координат объявления. Бонус плавно убывает, поэтому объявления из пригородов и соседних городов не отсекаются, как при жёстком фильтре по городу.

### Дообучение эмбеддера (`step4_finetune.py`)

- **Данные:** 300 000 пар «запрос с фильтрами → выбранное объявление» из train, без повторов одной и той же пары.
- **Функция потерь:** `MultipleNegativesRankingLoss` (контрастное обучение с in-batch negatives): в пачке из 128 пар каждый запрос учится быть ближе к своему объявлению, чем к 127 чужим.
- **Без повторов внутри пачки** (`BatchSamplers.NO_DUPLICATES`): если в одну пачку попадут два одинаковых запроса («маникюр») с разными мастерами, модель получит ложный сигнал «мастер №2 не подходит под маникюр». Сэмплер исключает такие случаи.
- **Параметры:** 1 эпоха, learning rate 2e-5, warmup 100 шагов, bf16, `max_seq_length=192`, seed 42.
- **Защита от утечки:** из обучения исключены и тексты валидационных запросов, и их верные объявления.

Веса итоговой формулы подобраны перебором по сетке на валидации. Оптимальный вес семантики после дообучения вырос с 0.85 до 0.95: модель стала лучше понимать запросы, и ей можно доверять больше, чем совпадению слов.

Библиотеки: PyTorch, sentence-transformers, transformers, datasets, accelerate, scikit-learn, pandas, pyarrow, numpy.

## 3. Как проверялось качество

**Разбиение по запросам, а не по строкам.** Если один и тот же текст запроса попадёт и в обучение, и в проверку, оценка будет завышена. Всё, что считается по train (центры локаций, дообучение), считается без валидационных запросов и без их верных объявлений.

**Две схемы валидации.**

1. *val1:* запросы из train, их выбранные объявления добавлены в корпус к `benchmark_items`. Схема хорошо предсказала платформу для гибрида без расстояния (0.7697 на валидации против 0.7663 на платформе), но сильно завысила эффект расстояния (0.8788 против 0.8049). Предположительная причина: добавленные объявления все оказываются «верными» для каких-то запросов, а в их городах обычных объявлений корпуса мало, поэтому географический бонус вытаскивал их слишком легко.
2. *val2 (итоговая):* 1000 запросов из train, чьи выбранные объявления **уже лежат** в `benchmark_items`. Корпус — только `benchmark_items`, без добавок, как в бенчмарке. Абсолютные числа стабильно завышают платформу примерно на 0.05, но порядок вариантов совпадает с платформой. Поэтому val2 использовалась для сравнения вариантов, а не для прогноза балла.

**История отправок:**

| # | Вариант | Валидация | Платформа |
|---|---|---|---|
| 1 | TF-IDF + малый бонус за город | — | 0.3807 |
| 2 | + семантика e5, бонус за город | val1: 0.7697 | 0.7663 |
| 3 | + расстояние (радиус 50 км), без бонуса за город | val1: 0.8788, val2: 0.8574 | 0.8049 |
| 4 | + популярность, радиус 200 км, город + расстояние | val2: 0.8794 | 0.8286 |
| 5 | + дообученный эмбеддер, вес семантики 0.95 | val2: 0.9339 | **0.8810** |

**Эффект дообучения на val2** (при `loc=2.0`, `dist=4.0`):

| Вес семантики w | Базовая e5 | Дообученная |
|---|---|---|
| 0.70 | 0.8622 | 0.8880 |
| 0.85 | 0.8794 | 0.9218 |
| 0.95 | 0.8656 | **0.9339** |
| 1.00 | 0.8439 | 0.9251 |

Новая идея отправлялась, только если давала на валидации прирост не меньше 0.01. Меньшие изменения считались шумом.

## 4. Найденные ошибки и что с ними сделано

**Ошибки в данных и постановке**

- *Жёсткие фильтры опасны.* «Вид услуги» совпадает в 98.4%, «Тип услуги» только в 93%. При одном-двух верных объявлениях на запрос каждое отсечённое объявление сильно бьёт по recall, поэтому все сигналы сделаны мягкими прибавками к оценке, а не фильтрами.
- *Фильтры записаны без разделителей* («Тип услуги Тату, пирсинг Вид услуги Красота, здоровье»), значения содержат запятые. Разбор сделан регулярным выражением до следующего известного ключа. Проверка на валидации: все значения «Вида услуги» из запросов распознаны.
- *Идентификаторы.* `query_id` и `item_id` читаются и пишутся строго как строки, CSV без индекса, формат проверяется `check_answer.py` перед каждой отправкой.

**Ошибки валидации**

- Первая схема (val1) завышала эффект расстояния на 0.07. Схема заменена на val2 с настоящим корпусом.
- Две гипотезы о причине не подтвердились и были проверены данными: отсутствие координат центра у локаций бенчмарка (у 100% запросов центр есть) и пропуски в координатах объявлений (меньше 0.05%).

**Ошибки модели (анализ промахов на val2, режим `err`, до дообучения)**

| Расстояние до центра | Объявлений | Recall | Промахов |
|---|---|---|---|
| до 10 км | 907 | 0.912 | ~80 |
| 10–50 км | 178 | 0.753 | ~44 |
| дальше 50 км | 40 | ~0.45 | ~22 |

- *Далёкие объявления.* Бонус только за точный город терял 17% пар с другим городом. Заменён на плавно убывающий бонус за расстояние: +0.07–0.10 на валидации, +0.04 на платформе. Узкий радиус (25 км) хуже, широкий (200 км) лучше.
- *Синонимы и смысловые связи:* «скупка» ↔ «выкуп», «вывоз диванов» ↔ «вывоз мебели», «космоэнергетика» ↔ «снятие порчи». Базовая e5 не знает языка Авито. Решено дообучением эмбеддера на парах из train: +0.055 на валидации, +0.052 на платформе.
- *«Толпа» в популярных запросах* («маникюр», «ногти», «портной»): в крупном городе сотни одинаково подходящих объявлений, и в 50 мест они не помещаются. Больше половины промахов лежат ближе 10 км к центру, то есть это ранжирование внутри города. Частично помогает популярность по числу отзывов. Это естественный потолок задачи.

**Инженерные ошибки в процессе**

- *Переполнение видеопамяти на Windows.* При обучении с пачкой 128 драйвер не выдал ошибку нехватки памяти, а незаметно вынес около 7 ГБ в общую (оперативную) память. Видеокарта показывала 100% загрузки, но работала медленно (обучение заняло 2 часа). Диагностика — Диспетчер задач, «Общая память графического процессора». Для ускорения можно заменить функцию потерь на `CachedMultipleNegativesRankingLoss(model, mini_batch_size=32)`, которая даёт тот же эффективный размер пачки при меньшем расходе памяти (итоговая модель обучена обычной версией).
- *Ложное совпадение при проверке воспроизводимости.* На одном из этапов `submit` сохранял ответ в другой файл, и сравнение показало 100%, сравнивая старый файл сам с собой. Ошибка найдена по времени изменения файлов, после чего проверка повторена честно (модель из архива, кэш удалён).

**Проверенные, но не принятые идеи**

- Явный бонус за совпадение «Вида услуги»: +0.006 на val2, ниже порога 0.01. В коде оставлен выключенным (`KIND=0`).
- Бонус только за точный город без расстояния: хуже на всех весах.
- Повторный подбор весов географии под дообученную модель: лучший вариант +0.002 на val2, в пределах шума, веса оставлены прежними.

## Что можно улучшить

- Жёсткие отрицательные примеры при дообучении (похожие, но не выбранные объявления из того же города) и больше эпох.
- Второй источник кандидатов для популярных запросов внутри города (отдельный топ по популярности и расстоянию) и объединение списков.
- Лемматизация (pymorphy) вместо обрезки слов в TF-IDF.

- Библиотеки: PyTorch, sentence-transformers, transformers, datasets, accelerate, scikit-learn, pandas, pyarrow, numpy, scipy.
