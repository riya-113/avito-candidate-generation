# Кандидатогенерация для услуг Авито

Тестовое задание в Data Science Bootcamp: по поисковому запросу достать из ~189 тыс. объявлений 50 кандидатов так, чтобы среди них оказалось то, что пользователь в итоге выбрал. Метрика Recall@50.

Итог на платформе: **0.8810**. Начинала с 0.38 на простом TF-IDF.

Коротко, что внутри: эмбеддинги multilingual-e5-base, которые я дообучила на парах из train, плюс TF-IDF, плюс бонус за близость объявления к городу запроса, плюс небольшой бонус за число отзывов.

## Как запустить

Нужен Python 3.12 и видеокарта NVIDIA (у меня RTX 5080 на 16 ГБ, Windows).

```bash
python -m venv .venv
.venv\Scripts\activate
pip install torch==2.11.0 --index-url https://download.pytorch.org/whl/cu128
pip install -r requirements.txt
```

Данные (`train.parquet`, `benchmark_queries.parquet`, `benchmark_items.parquet`) положить в папку `data/`.

Дообученная модель весит ~1 ГБ, в GitHub не влезает, поэтому она на Яндекс Диске: https://disk.yandex.ru/d/2uQTXr-jab4YpA
Архив распаковать в `models/`, должно получиться `models/e5-avito/model.safetensors`:

```powershell
Expand-Archive e5-avito.zip -DestinationPath models
```

Дальше:

```bash
python step3_hybrid.py submit 0.95 2.0 4.0
python check_answer.py
```

Получится `answer.csv`. Я проверяла так: удалила кэш эмбеддингов, распаковала модель из архива заново, запустила — файл совпал с отправленным на 100%. На другой видеокарте из-за fp16 в топ-50 могут поменяться единичные объявления.

Если хочется обучить модель самой: `python step4_finetune.py`, у меня заняло около двух часов. Веса выйдут немного другие, так что ответ может чуть отличаться.

Интернет нужен только для обучения (скачать базовую e5 с Hugging Face). Сам поиск работает локально, никаких внешних API.

## Какие данные и признаки взяла и почему

Первым делом посмотрела на данные, и пара вещей сразу поменяла план.

Хотела фильтровать по категории, но оказалось, что почти весь корпус (99%) — это одна категория 114. Фильтр ничего не отсекает, а у 9% запросов категория вообще пустая. Выкинула.

В заголовках мало слов (медиана 4), вся конкретика в параметрах объявления: «Вид услуги», «Тип услуги», прайс. Поэтому в текст объявления беру заголовок, параметры и начало описания.

У запроса есть фильтры вроде «Вид услуги Красота, здоровье». Они почти всегда (98.4%) дословно совпадают с параметрами выбранного объявления. Жёстко фильтровать по ним не стала, а просто добавила в текст запроса. Почему не фильтр — ниже.

Самое неожиданное: город. В 83% случаев человек выбирает исполнителя из своего города, и одна эта штука подняла метрику сильнее, чем все эмбеддинги вместе взятые. У запроса есть только id локации без координат, поэтому «центр» каждой локации я посчитала сама — как медиану координат объявлений, которые там выбирали в train.

Ещё добавила число отзывов: при прочих равных люди чаще выбирают тех, у кого отзывы есть.

Train как справочник «запрос → ответ» не работает: объявлений из train в корпусе всего 6.6%. Зато он отлично подошёл для дообучения модели.

## Модели

Для каждого объявления считаю скор и беру топ-50:

```
score = 0.95 * смысл + 0.05 * слова
      + 2.0 * (тот же город)
      + 4.0 * exp(-расстояние_км / 200)
      + 1.0 * популярность
```

Смысл и слова перед сложением нормирую внутри запроса (z-score), иначе у них разные шкалы. Ищу полным перебором на GPU, без приближённых индексов — корпус небольшой, а полноту терять не хотелось.

- **Слова** — TF-IDF, слова обрезаны до 5 букв (вместо лемматизации, чтобы «наращивание» и «наращивании» совпадали).
- **Смысл** — multilingual-e5-base. Сначала брала готовую, потом дообучила.
- **Расстояние** — сначала был бонус только за точное совпадение города, потом поменяла на плавное затухание по расстоянию, чтобы не терять пригороды.

Дообучение: 300 тыс. пар «запрос → выбранное объявление» из train, MultipleNegativesRankingLoss. Смысл такой: в пачке 128 пар, и каждый запрос учится быть ближе к своему объявлению, чем к остальным 127. Одинаковые запросы в одну пачку не кладу (NO_DUPLICATES), иначе модель учила бы, что второй мастер маникюра «не подходит» к маникюру. Одна эпоха, lr 2e-5.

## Как проверяла качество

Делила по тексту запроса, а не по строкам, чтобы один и тот же запрос не попал и в обучение, и в проверку.

С валидацией пришлось повозиться. Первая версия (подкладывала правильные объявления из train в корпус) неплохо совпадала с платформой, пока я не добавила расстояние. Тут она обещала 0.88, а платформа дала 0.80. Я проверила две гипотезы, почему так (нет центров у локаций, битые координаты) — обе мимо. В итоге переделала валидацию: взяла только те запросы из train, чьи объявления и так лежат в корпусе, и искала по настоящему корпусу без добавок. Новая валидация стабильно завышает примерно на 0.05, но порядок вариантов совпадает с платформой, так что сравнивать по ней можно.

Правило для себя: отправляю на платформу, только если на валидации прирост хотя бы 0.01.

| | что сделала | валидация | платформа |
|---|---|---|---|
| 1 | TF-IDF | — | 0.3807 |
| 2 | + e5 + бонус за город | 0.7697 | 0.7663 |
| 3 | + расстояние вместо города | 0.8574 | 0.8049 |
| 4 | + отзывы, город и расстояние вместе | 0.8794 | 0.8286 |
| 5 | + дообученная e5 | 0.9339 | 0.8810 |

## Какие ошибки нашла и что с ними сделала

Разобрала промахи на валидации. Больше половины из них — объявления в пределах 10 км от центра, то есть проблема не в географии, а в ранжировании внутри города. Там два типа:

- **Синонимы.** «Скупка» и «выкуп», «вывоз диванов» и «вывоз мебели», «космоэнергетика» и «снятие порчи». Готовая e5 такого не знает, именно это вылечило дообучение (+0.05 на платформе).
- **«Толпа».** По запросам вроде «маникюр» в большом городе сотни одинаково подходящих мастеров, и 50 мест на всех не хватит. Тут, по-моему, есть естественный потолок, отзывы помогают только чуть-чуть.

Почему не жёсткие фильтры: верных объявлений на запрос обычно одно-два, поэтому любой промах фильтра сразу бьёт по метрике. Даже 98% совпадения — это 2% запросов, которые я бы потеряла на ровном месте. Поэтому всё сделано мягкими бонусами.

Что пробовала и не взяла:
- отдельный бонус за совпадение «Вида услуги» — +0.006, в пределах шума;
- бонус за подкатегорию, которую обычно выбирают по похожим запросам, — тоже шум. Похоже, дообученная модель это уже выучила;
- переподбор весов под дообученную модель — +0.002, оставила как было.

Была ещё идея поднимать объявления, которые часто выбирали в train. На моей валидации она бы выглядела отлично, но только потому, что валидация как раз и собрана из таких объявлений. Честно проверить не получилось, поэтому не стала рисковать.

Из технических граблей:
- при обучении кончилась видеопамять, но Windows не выдала ошибку, а тихо унесла 7 ГБ в обычную память, и всё стало ползти. Заметила по диспетчеру задач. Для следующего обучения поставила CachedMultipleNegativesRankingLoss — стало раза в четыре быстрее;
- один раз проверка воспроизводимости показала 100%, потому что скрипт сохранял ответ в другой файл, а я сравнивала старый сам с собой. Поймала по времени изменения файлов, перепроверила уже честно.

## Что бы сделала дальше

- Трудные негативы при дообучении. Уже пробовала: главная сложность в том, что «похожее, но не выбранное» объявление часто на самом деле тоже подходит.
- Отдельный источник кандидатов для популярных запросов.
- Нормальная лемматизация вместо обрезки слов.
