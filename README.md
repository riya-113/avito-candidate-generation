# Кандидатогенерация для категории «Услуги» (Авито, Recall@50)

Задача: для каждого поискового запроса выбрать из корпуса 189 212 объявлений до 50 кандидатов так, чтобы в них попали объявления, которые пользователь в итоге выбрал. Метрика — Recall@50.

**Итоговый результат на платформе: Recall@50 = 0.8286.**

## Быстрый запуск (воспроизведение answer.csv)

Требования: Windows/Linux, Python 3.12, видеокарта NVIDIA с CUDA (решение проверялось на RTX 5080, 16 ГБ).

```bash
python -m venv .venv
.venv\Scripts\activate            # Linux: source .venv/bin/activate
pip install torch==2.11.0 --index-url https://download.pytorch.org/whl/cu128
pip install -r requirements.txt
```

Положите три файла данных в папку `data/`:
`train.parquet`, `benchmark_queries.parquet`, `benchmark_items.parquet`.

```bash
python step3_hybrid.py submit 0.85 2.0 4.0   # создаёт answer.csv
python check_answer.py                       # проверка формата
```

При первом запуске скачиваются открытые веса модели `intfloat/multilingual-e5-base` с Hugging Face (один раз, дальше работает локально). Во время работы решения внешние API не вызываются. Эмбеддинги кэшируются в `cache/`. Кодирование корпуса занимает около 2 минут на RTX 5080.

Воспроизводимость проверена «с нуля»: после удаления кэша эмбеддингов и без переменных окружения команда выше даёт `answer.csv`, совпадающий с отправленным на платформу на 100% (проверка скриптом `compare.py`). Эмбеддинги считаются в fp16 на GPU, поэтому на видеокарте другой архитектуры последние знаки могут немного отличаться, что способно поменять единичные объявления в топ-50.

После первого запуска модель лежит в локальном кэше Hugging Face, и решение можно запускать полностью офлайн, выставив переменную окружения `HF_HUB_OFFLINE=1`.

## Структура

| Файл | Что делает |
|---|---|
| `check_env.py` | проверка окружения, GPU и данных |
| `step1_eda.py`, `step1b_checks.py` | разведочный анализ данных |
| `step2_baseline.py` | лексический бейзлайн TF-IDF и общие функции |
| `step3_hybrid.py` | итоговое решение: гибридный поиск, валидация, анализ ошибок, `submit` |

Режимы `step3_hybrid.py`: `val2` — валидация, `err` — анализ ошибок, `submit w loc dist` — ответ для бенчмарка.

## 1. Данные и признаки

Сначала проведён разведочный анализ (EDA), от его результатов зависел выбор признаков.

- **Категория выброшена.** 99% корпуса лежит в категории 114, и в 497 620 из 497 673 пар train категория запроса и объявления одинакова. У 9% запросов бенчмарка категория пустая (0), так что жёсткий фильтр по ней не отсекает ничего полезного и способен только навредить.
- **Текст объявления:** заголовок, параметры (`item_infm_params_text`) и начало описания. Медианная длина заголовка 4 слова, этого мало. Конкретика («Вид услуги», «Тип услуги», названия услуг из прайса) лежит в параметрах. Описание длинное и шумное, но добавляет слова, которых нет в других полях.
- **Текст запроса:** `search_query` плюс фильтры `search_infm_params_text`. Фильтр «Вид услуги …» дословно совпадает с параметрами выбранного объявления в 98.4% случаев.
- **География:** город запроса совпадает с городом выбранного объявления в 83% пар train. У запроса есть только `search_location_id`, поэтому координаты «центра» каждой локации восстановлены по train как медиана координат объявлений, выбранных в этой локации.
- **Популярность:** число отзывов `item_rating_reviews_count`.
- **История кликов как справочник ответов не используется.** По `item_id` в корпусе есть только 6.6% объявлений из train, а тексты 63% запросов бенчмарка в train не встречаются.

## 2. Модели и алгоритм

Для каждой пары запрос–объявление считается итоговая оценка, и берутся 50 объявлений с максимальной оценкой. Поиск точный (перебор всего корпуса на GPU через матричное умножение), без приближённых индексов, чтобы не терять полноту.

```
score = 0.85 · z(семантика) + 0.15 · z(TF-IDF)
      + 2.0 · [город объявления == город запроса]
      + 4.0 · exp(−расстояние_км / 200)
      + 1.0 · log(1 + отзывы) / log(1 + max_отзывы)
```

- **Семантика:** `intfloat/multilingual-e5-base` (open-source, sentence-transformers), fp16 на GPU. Текст объявления: `passage: заголовок. Вид услуги. Тип услуги. описание[:500]`, запрос: `query: текст + фильтры`. Полные параметры в эмбеддер не подаются: они длинные и заполняют лимит токенов адресами и списками марок авто.
- **TF-IDF:** слова обрезаются до 5 символов (грубая замена лемматизации, «наращивание» ≈ «наращивании»), `sublinear_tf`, `min_df=2`. Заголовок повторён трижды для большего веса.
- **z(·)** — нормировка оценок внутри запроса (среднее 0, разброс 1), чтобы складывать сигналы разной природы.
- **Расстояние** — от центра локации запроса до координат объявления. Бонус плавно убывает, поэтому объявления из пригородов и соседних городов не отсекаются, как при жёстком фильтре по городу.

Веса подобраны перебором по сетке на валидации.

Библиотеки: PyTorch, sentence-transformers, scikit-learn, pandas, pyarrow, numpy.

## 3. Как проверялось качество

**Разбиение по запросам, а не по строкам.** Если один и тот же текст запроса попадёт и в обучение, и в проверку, оценка будет завышена. Всё, что считается по train (центры локаций), считается без валидационных запросов и без их верных объявлений.

**Две схемы валидации.**

1. *val1:* запросы из train, их выбранные объявления добавлены в корпус к `benchmark_items`. Схема хорошо предсказала платформу для гибрида без расстояния (0.7697 на валидации против 0.7663 на платформе), но сильно завысила эффект расстояния (0.8788 против 0.8049). Предположительная причина: добавленные объявления все оказываются «верными» для каких-то запросов, а в их городах обычных объявлений корпуса мало, поэтому географический бонус вытаскивал их слишком легко.
2. *val2 (итоговая):* 1000 запросов из train, чьи выбранные объявления **уже лежат** в `benchmark_items`. Корпус — только `benchmark_items`, без добавок, как в бенчмарке. Абсолютные числа завышают платформу примерно на 0.03–0.05, но порядок вариантов совпадает с платформой. Поэтому val2 использовалась для сравнения вариантов, а не для прогноза балла.

**История отправок:**

| # | Вариант | Валидация | Платформа |
|---|---|---|---|
| 1 | TF-IDF + малый бонус за город | — | 0.3807 |
| 2 | + семантика e5, бонус за город | val1: 0.7697 | 0.7663 |
| 3 | + расстояние (радиус 50 км), без бонуса за город | val1: 0.8788, val2: 0.8574 | 0.8049 |
| 4 | + популярность, радиус 200 км, город + расстояние | val2: 0.8794 | **0.8286** |

Новая идея отправлялась, только если давала на валидации прирост не меньше 0.01. Меньшие изменения считались шумом.

## 4. Найденные ошибки и что с ними сделано

**Ошибки в данных и постановке**

- *Жёсткие фильтры опасны.* «Вид услуги» совпадает в 98.4%, «Тип услуги» только в 93%. При одном-двух верных объявлениях на запрос каждое отсечённое объявление сильно бьёт по recall, поэтому все сигналы сделаны мягкими прибавками к оценке, а не фильтрами.
- *Фильтры записаны без разделителей* («Тип услуги Тату, пирсинг Вид услуги Красота, здоровье»), значения содержат запятые. Разбор сделан регулярным выражением до следующего известного ключа. Проверка на валидации: все значения «Вида услуги» из запросов распознаны.
- *Идентификаторы.* `query_id` и `item_id` читаются и пишутся строго как строки, CSV без индекса, формат проверяется `check_answer.py` перед каждой отправкой.

**Ошибки валидации**

- Первая схема (val1) завышала эффект расстояния на 0.07. Схема заменена на val2 с настоящим корпусом.
- Две гипотезы о причине не подтвердились и были проверены данными: отсутствие координат центра у локаций бенчмарка (у 100% запросов центр есть) и пропуски в координатах объявлений (меньше 0.05%).

**Ошибки модели (анализ промахов на val2, режим `err`)**

| Расстояние до центра | Объявлений | Recall | Промахов |
|---|---|---|---|
| до 10 км | 907 | 0.912 | ~80 |
| 10–50 км | 178 | 0.753 | ~44 |
| дальше 50 км | 40 | ~0.45 | ~22 |

- *Далёкие объявления.* Бонус только за точный город терял 17% пар с другим городом. Заменён на плавно убывающий бонус за расстояние: +0.07–0.10 на валидации, +0.04 на платформе. Узкий радиус (25 км) хуже, широкий (200 км) лучше.
- *«Толпа» в популярных запросах* («маникюр», «ногти», «портной»): в крупном городе сотни одинаково подходящих объявлений, и в 50 мест они не помещаются. Больше половины промахов лежат ближе 10 км к центру, то есть это ранжирование внутри города. Частично помогает популярность по числу отзывов.
- *Синонимы и смысловые связи:* «скупка» ↔ «выкуп», «вывоз диванов» ↔ «вывоз мебели», «космоэнергетика» ↔ «снятие порчи». Частично закрывает e5, остальное требует дообучения.

**Проверенные, но не принятые идеи**

- Явный бонус за совпадение «Вида услуги»: +0.006 на val2, ниже порога 0.01. В коде оставлен выключенным (`KIND=0`).
- Бонус только за точный город без расстояния: хуже на всех весах.

## Что можно улучшить

- Дообучить эмбеддер контрастным обучением на парах запрос–объявление из train. Это должно закрыть ошибки на синонимах, главный резерв решения.
- Второй источник кандидатов для популярных запросов внутри города (отдельный топ по популярности и расстоянию) и объединение списков.
- Лемматизация (pymorphy) вместо обрезки слов в TF-IDF.
